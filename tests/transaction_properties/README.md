# Property testing transactions against consensus

This package draws transactions with [`pgregory.net/rapid`](https://pkg.go.dev/pgregory.net/rapid)
and pushes them **straight into consensus through the test-only API, bypassing the transaction
pool**. It then checks what the network did with each one against three independent oracles.

It covers two families of transaction: ordinary ones, which pay for their own gas, and **sponsorship
requests**, which offer nothing for it and are covered by a gas-subsidies fund instead. The second is
the first with its gas price taken away, so it is generated by wrapping the first generator rather
than by a second one — see [Domains](#domains).

Bypassing the pool is the whole point. The pool is the component that normally refuses malformed
transactions, so with it out of the way the pressure falls on event validation, the block formation
filter and the state processor — the places where being wrong means a chain split rather than a
rejected RPC request. This path is reachable in production by a validator proposing its own
transactions, or by any node run with `--disable-txPool-validation`.

This is **property testing, not fuzzing**. Each drawn input is checked against stated properties
using a model, and a failure shrinks to a minimal counterexample naming its seed. The repo's
`Fuzz*` targets (see [FUZZING.md](../../FUZZING.md)) remain the right tool for coverage-guided
crash search.

## Running it

```sh
go test ./tests/transaction_properties/                       # 200 batches per scenario, ~3 min
go test ./tests/transaction_properties/ -v                    # + the distribution per scenario
go test ./tests/transaction_properties/ -rapid.checks=2000    # a longer search
go test ./tests/transaction_properties/ -rapid.seed=1436157575314665811   # replay one failure

go test ./tests/transaction_properties/...                    # + the unit tests of the harness
go test ./tests/transaction_properties/ -run Sponsored -v     # the sponsorship scenarios alone
```

No flags, and no way to make it fail over something already known: a transaction that provokes a
defect the client has not fixed is not injected at all — see [Skipping](#skipping). A scenario is one
network: each of the three forks on its own, five more with gas subsidies enabled, and three carrying
bundles.

The nodes are silenced, because every batch deliberately made too large for one event is logged at
ERROR as `Self-event connection failed` — hundreds of times a run, for something the test provokes on
purpose and reports itself. `SONIC_VERBOSITY=3 go test ./tests/transaction_properties/` brings the
client's own logging back.

A deeper search runs nightly from [CI/transaction-properties.jenkinsfile](../../CI/transaction-properties.jenkinsfile),
which draws 5000 batches per scenario instead of 200, after rebasing the branch onto `SonicVersion` of
`SonicRepository` — main of this repository unless the build says otherwise. It only runs the command:
nothing about the test differs there, only how long it searches, and whatever the test says is the
build's result.

## Domains

The harness knows nothing about any particular kind of transaction. What one family of transactions
is, how it is priced, what it needs arranged on chain and what only it can check, is a `core.Domain`,
and the packages here are one apiece:

```text
  tests/transaction_properties/          the property tests, and the wiring
    core/        the harness: what a transaction is, how it is built, the model, the invariants,
                 the account pool, the block barrier, the runner. No knowledge of any family.
    regular/     ordinary transactions: the five types, each declared as the capabilities it
                 carries, and the rules that price one against its sender's balance.
    subsidies/   gas subsidies, layered over another domain rather than beside it.
    bundles/     transaction bundles, a container: a batch inside a batch.
```

A domain contributes seven things, and a domain that wraps another passes each one through:

| `core.Domain` | `regular` | `subsidies` | `bundles` |
| --- | --- | --- | --- |
| `Batch()` | draws the batch | `Sponsoring(inner.Batch())`: takes the gas price off part of what the inner domain drew | `Bundling(inner.Batch())`: replaces one of them with an envelope carrying a batch of its own |
| `Pricing()` | fee cap against the base fee, balance against `buyGas` | fund coverage for a request, the inner rules for everything else | a carrier never enters a block; before Brio, the inner rules |
| `Prepare()` | nothing to arrange | pays into the sponsorship fund of each sender with a request | builds the bundle: nonces, plan, marker, gas, signatures |
| `Skip()` | a creation whose value its sender may not hold — defect [1] | the inner rules; what must not be *sponsored* is dropped in the generator instead | the inner rules, for the batch and for every bundle's contents |
| `Extra()` | nothing | nothing: a follow-up is an internal transaction | the contents, which reach a block without having been injected |
| `Check()` | nothing only it can see | the follow-up transaction each mode calls for, and the funds | all-or-nothing, and the record the chain keeps of it |
| `Notes()` | one line per defect it skips for | its own, and the inner domain's | its own, and the inner domain's |

`Skip` is asked once per drawn transaction, with the sender's state and the base fee, and whatever it
names is dropped before any nonce is assigned — so a skipped transaction leaves no hole in the sequence
the rest of the batch is judged against. See [Skipping](#skipping).

That is the whole seam. `core.PredictTx` keeps its flat table of structural rules — signature, nonce,
intrinsic gas, type-level malformity — and takes the rules deciding whether a transaction can *pay*
from the domain, because that answer is what differs: one pays from a balance, the other from a fund.

## Sponsorship

A sponsorship request is an ordinary transaction with a maximum gas price of zero and a recipient.
The generator therefore does not build one: it draws an ordinary batch and zeroes the price fields of
part of it, in place, on the drawn spec.

```go
specs := inner.Draw(t, "batch")          // whatever the ordinary generator drew
spec.(core.ZeroablePrice).ZeroPrices()   // the same spec, now asking to be sponsored
```

Zeroing the drawn spec rather than wrapping it is not a detail. A wrapper embedding `core.TxSpec` and
overriding `FeeCap()` would disagree with `TxData()`, which reads the concrete fields, and would break
the optional capabilities, which are fetched by type assertion: a static wrapper implements
`WithAuths` for every type or for none, so a sponsored legacy transaction would be judged as a
set-code transaction with an empty authorization list. `ZeroPrices` replaces the fields rather than
writing through them, because a drawn `*big.Int` is shared between iterations.

A **contract creation** is deliberately left unsponsored, and dropped from the batch if the ordinary
fee caps — which include zero — made a request of one anyway: production refuses to sponsor one, so
the ordinary rules already predict what happens to one offering nothing. A transaction whose **value
is wider than 256 bits** is kept out of the sponsored set the same way, because a request carrying one
panics the node — defect [4]. Both are still injected as ordinary transactions; only the request of
that shape is dropped, which is what `unsponsorable` is for and why this is not `Skip`.

### Who pays, and what follows

Which registry is installed decides who pays. That is a property of the network, not of a batch, so
it is a scenario rather than a draw:

| Scenario | Registry | Forks | Coverage depends on | Follows a sponsored transaction |
| --- | --- | --- | --- | --- |
| fund-backed (mode 1) | the reference registry deployed in genesis | all three | what the fund holds | `deductFees`, charging `(gasUsed + 210k) × baseFee` |
| network-sponsored (mode 2) | `tests/contracts/network_sponsor` | Brio | nothing, every request is covered | nothing |
| with tracking (mode 3) | `tests/contracts/network_sponsor_tracking` | Brio | nothing, every request is covered | `track`, recording `(gasUsed + 230k) × baseFee` |

The fund-backed scenario runs on every fork, because it is the one whose answer depends on money and
because the structural rules a request still has to satisfy are fork-dependent. The other two run on
Brio alone: once a request is covered they behave the same on every fork, and the fork-dependent half
is already covered by the fund-backed runs. Each of their registries answers the same mode for every
caller, which is what keeps them free of per-iteration setup.

### Funding, and the three bands

Each iteration draws a level per sender that has a request — pay nothing, pay exactly what the batch
asks, or pay eight times that — and pays it into that sender's account fund. Every payment of an
iteration is sent before any of them is waited for, so funding three senders costs about one block
rather than three, and paying nothing costs none at all.

The payer is one account of the pool, claimed for the life of the network and never released, so it is
never an account under observation. It cannot be the session sponsor: that account also drives every
block of the barrier, and a few hundred iterations paying several funds apiece drain it — which is
exactly how this was found, at iteration 138 of a 200-iteration run.

Only account funds are ever paid into; the run asserts at startup that the global and bootstrap funds
are empty, so a coverage decision follows from one balance.

Coverage is then predicted in three bands, at the base fee the batch is judged against:

```text
  funds < ¼ × (this request alone)          ──▶  Dropped
  funds < 4 × (all this sender's requests)  ──▶  {Dropped or Executed}
  otherwise                                 ──▶  the structural rules decide alone
```

The middle band is not vagueness. Within one block the chosen fund is charged between requests,
`chooseFund` tests the gas *limit* while `deductFees` charges the gas *used*, and the order the
requests reach the block in is the scrambler's to choose. Naming one outcome there would manufacture
failures; the bands still catch every real defect, because a request that must not execute but does,
or must execute but does not, falls outside them.

### What the accounting did not need

Nothing. A sponsored transaction's receipt reports an effective gas price of zero, so the existing
conservation check — balance moves by gas × price + blob fee + value transferred — already says the
sender pays for its value alone. The fund's side of it is the new part, and it is the same shape:

```text
  fundBefore − fundAfter == Σ what the follow-ups in the blocks said they charged
```

One thing did need the model, though, and it is worth knowing about: **a sponsored transfer can empty
its sender**, which an ordinary one cannot. An ordinary transaction buys its gas before it transfers,
so a transfer that would leave its sender unable to pay reverts instead; a sponsored one pays nothing
and can hand over the lot, and the next transaction of that sender then cannot buy gas. The model
walks a sender's run in nonce order with a running balance, so this is a band there too: once the
balance can no longer back a transaction, that one and everything behind it become uncertain.

## Testing the harness itself

The model, the capabilities, the builder, the pool, the block checks and the sponsorship rules are unit
tested without a network, so a change to the harness fails in milliseconds rather than surfacing as a
puzzling property failure minutes later:

```sh
go test ./tests/transaction_properties/...     # the three harness packages, and the property tests
go test ./tests/transaction_properties/core/ ./tests/transaction_properties/regular/ \
        ./tests/transaction_properties/subsidies/          # the unit suites alone
```

The whole unit suite is 200 cases in under a tenth of a second, and none of them starts a node. What
they cover:

| File | Covers |
| --- | --- |
| `regular/model_test.go` | the gas schedules against known values, prices and costs, nonce assignment and ordering, every rule in `core.PredictTx`, and that the fork gates apply |
| `regular/spec_test.go` | each capability's field definition, saturation of the narrow ones, and that a type lacking a capability really lacks it |
| `regular/build_test.go` | that a spec becomes a transaction of its own type, recipient resolution, authorization choices, and that **every signing defect really is one** — recovery either fails or lands on an address holding nothing |
| `regular/generators_test.go` | rapid applied to the generators themselves: whatever is drawn is internally consistent and buildable, and the type weighting is what it claims |
| `regular/known_defects_test.go` | which forks a sighting fails on, that the report names only what the run reproduced, and that the skip policy keeps out exactly the creations defect [1] can bite |
| `core/invariants_test.go` | the block checks against deliberately spoiled receipts, that the nonce must match exactly, and that the balance is tolerant exactly where a defect applies |
| `core/pool_test.go` | key determinism, that untouched accounts come first, and that a dirty one is only reused once they run out |
| `subsidies/sponsor_test.go` | rapid applied to the transform: what comes out is coherent and buildable, every type gets sponsored, the shared generator values are not written through, and what must not be sponsored is dropped |
| `subsidies/model_test.go` | the three coverage bands, that the network modes need no fund, that anything paying its own way falls through to the inner rules, and the overhead arithmetic of each mode |
| `subsidies/invariants_test.go` | the follow-up each mode calls for, against every way of spoiling one: missing, wrong kind, one wei off, or charging a transaction that paid for itself |

Why the tests of the model live in `regular` rather than in `core`: a rule needs a transaction to
judge, and the transaction types are that package's. Only the checks needing no spec at all stay in
`core`.

The two oracles that need a chain — the replay and the outcome comparison — are exercised by the
property tests themselves, not here.

### Outcomes

| Outcome | Decided by | Observable |
| --- | --- | --- |
| `EventRejected` | gate 1 | `ForceEmitAll` errors; **no** transaction of the batch may have any effect |
| `Dropped` | gate 2 **or** gate 3 | in no block, no receipt, sender untouched |
| `Executed` | — | receipt exists; nonce +1, balance −(gasUsed × effectiveGasPrice + blobFee + value) |

Gates 2 and 3 cannot be told apart from outside the node, so the model deliberately reports only
three outcomes. Where a gate genuinely has two legal answers — a fee cap within a factor of four of
a base fee that moves while the batch is in flight, a balance that close to what `buyGas` needs, two
transactions competing for one nonce — the prediction is a *set*. Naming one answer there would
manufacture false failures; the set still catches every real defect, because a transaction that must
not execute but does, or must execute but does not, falls outside it.

## What is generated

A transaction type is declared as the capabilities it carries. Each capability is a struct owning the
fields it contributes and defining what they mean, so what a type cannot carry is *unrepresentable*
rather than merely unused — a legacy transaction has no access-list field to leave empty, and no tip
cap that could sit above its fee cap.

```text
  capability            fields                 defines
  ─────────────────────────────────────────────────────────────────────────────
  envelope              SenderIdx 0..2         index into the accounts this
                        Nonce                  iteration claimed — never an
                        NonceGapSize 1..4      address, so shrinking cannot
                        GasLimit               collapse onto one dirty account
                        Signing
  payload               DataLen, DataNonZero   data(): all-00 or all-01, which
                                               are priced differently
  optionalRecipient     To                     isCreate(): To may be empty
  requiredRecipient     To                     isCreate() = false: no creation
  wideValue             Value                  value(): big.Int, >256 bits fits
  narrowValue           Value                  value(): uint256, saturating
  singlePrice           GasPrice               feeCap() == tipCap()
  widePrices            GasFeeCap, GasTipCap   feeCap(), tipCap(): big.Int
  narrowPrices          GasFeeCap, GasTipCap   feeCap(), tipCap(): saturating
  accessListEntries     AccessListLen 0..8     accessList()
  blobHashList          BlobHashLen 0..2       blobHashes(): any is malformed
  authList              Auths 0..3             auths(): empty is malformed

                 envelope + payload
                         │
     ┌───────────────────┼─────────────────┬─────────────────┐
     v                   v                 v                 v
  legacyTx          accessListTx      dynamicFeeTx     blobTx     setCodeTx
  optionalRecipient optionalRecipient optionalRecipient requiredRecipient
  wideValue         wideValue         wideValue         narrowValue
  singlePrice       singlePrice       widePrices        narrowPrices
                    accessList        accessList        accessList
                                                        blobHashList  authList
```

The model asks for a capability a type may lack through an optional interface (`withAccessList`,
`withBlobHashes`, `withAuths`), so absence is expressed by absence.

Each type draws itself, calling the draw of every capability it embeds and taking the gas limit last,
since that is drawn *relative to the intrinsic cost of everything above it*:

```go
func (s *blobTx) draw(t *rapid.T, env genEnv) {
	s.envelope.draw(t, env)
	s.payload.draw(t, env)
	s.requiredRecipient.draw(t, env)
	s.narrowValue.draw(t, env)
	s.narrowPrices.draw(t, env)
	s.accessListEntries.draw(t, env)
	s.blobHashList.draw(t, env)
	s.GasLimit = drawGasLimit(t, env, s)
}
```

`genEnv` is the state every draw is handed and takes from what its own fields need: the network, how
many senders the batch shares, the gas this transaction may spend, and which transaction of the batch
it is (which labels the draw, so a failure report says where a value came from).

The interesting value ranges: gas limits at `{0, TxGas±1, legacy±1, revision±1, floor±1, +30k}` so
every boundary is reachable; fee caps at `{0, 1, viable, generous, >256 bits}`, never near the base
fee, which moves as blocks are produced and would make the outcome depend on timing; values
straddling the pooled balance `{0, 1, B/2, B−1, B, B+1, 2B, 30..33 raw bytes}`; and a transaction
type one above the fork's maximum, so the event-level rejection is reachable — drawn only one
transaction in nine, because a batch containing one is refused whole and at even weight it would cost
Sonic, the one fork where such a type exists, about half the coverage of everything downstream.

This covers the three dimensions the package set out to reach: **semantic invalidity** (nonce, gas,
fees, value, data), **invalid signature and sender** (`Signing`), and **type-level malformity** (blob
hashes, an empty authorization list, a type above the fork's max). The sponsored scenarios add a
fourth, orthogonal to all of them: **who pays** — every one of those defects is drawn again over a
transaction whose gas somebody else was asked to cover.

Raw byte corruption of the RLP is deliberately out of scope — that is a decoder fuzzing problem, and
the test-only API decodes before any of the layers above are reached.

Draws are weighted towards *valid* — mostly correct signatures, mostly correct nonces, mostly
sufficient gas — because the interesting bugs live in valid-mixed-with-invalid batches. A generator
producing uniform garbage never reaches execution at all.

The weighting is done by listing a value more than once, since `SampledFrom` and `OneOf` pick an
entry by index. That makes the ratios **approximate rather than nominal**: rapid draws the index with
a bias towards the front of the list, so an earlier entry gets somewhat more than its share — eight
`SignCorrect` entries of thirteen come out at about 71 %, not 62 %. The order is therefore part of
the intent: what is worth drawing most goes first, which is also the direction a failing case shrinks
towards. A typical run lands around 11-16 % /
69-73 % / 13-14 % across the three outcomes on Allegro and Brio, and around 38 % / 48 % / 12 % on
Sonic, which refuses more batches outright because it is the only fork with a representable
transaction type above its maximum.

## Two design decisions worth knowing

### Absence is confirmed in blocks, not seconds

"This transaction must never execute" cannot be a wall-clock timeout — that is flaky on a loaded
machine and slow when it passes. [core/barrier.go](core/barrier.go) instead spends a budget of
`ConfirmationBlocks = 2` blocks and declares absent whatever still has no receipt. Two rather than
one, because a forced event's transactions land in the next block formed *after* the event is
processed, so a one-block budget would race with a block already being sealed and report a merely
late transaction as absent.

The blocks must be *driven*, not waited for: Sonic paces empty blocks, so an idle network would take
two full skip periods. Each block is forced with one ordinary endowment from the session sponsor,
which is never an account under test.

### Accounts are funded in genesis, and the cost is drawn instead of the balance

Endowing accounts per iteration would dominate the runtime — every endowment is a transaction, so
the per-iteration cost becomes block time rather than RPC time. Instead [core/pool.go](core/pool.go) derives
4096 keys from a fixed seed, funds all of them in the genesis JSON with a constant `1e24` wei, and
hands them out from a pool. Zero transactions, zero blocks, every account at nonce 0.

"Transactions can be arbitrarily expensive" then stops being a funding problem: a transaction whose
cost exceeds any conceivable balance simply must be `Dropped`, and no amount of funding changes
that. With a *known constant* balance the model compares exactly, and the generator concentrates the
cost distribution just below, at and just above it. Accounts are returned after every iteration —
untouched ones first, so a shrink replay is more likely to see what the original run saw — which is
why the pool cannot run dry.

The size is about *coverage over time*, not about running out. An account a transaction executed from
never becomes untouched again, while the generator keeps drawing costs against the constant
`AccountBalance` — so once a run is handed dirty accounts, the cases straddling the affordability
boundary no longer straddle anything. At roughly one account dirtied every three iterations, 4096
keeps a run of ten thousand iterations on accounts whose balance the model knows exactly; the nightly
5000 stays well inside that. The `account pool:` line at the end of a run says how far it got.

```text
  genesis (one bulk state write, no blocks)
    4096 accounts × 1e24 wei, all at nonce 0
        │
        │  Claim(3)                            Release(dirty?)
        v                                            ^
   ┌─────────────┐   iteration    ┌──────────────┐    │
   │ untouched   │───────────────▶│ in use by    │────┘
   │ (preferred) │◀───────────────│ one iteration│  clean → untouched
   └─────────────┘   nothing      └──────────────┘  executed → used
                     executed
```

## Skipping

A transaction that provokes a defect the client has not fixed is dropped before it is injected, so a
run stays green and says in one line what it stepped around:

```text
  12 kept out of their batch: [1] a contract creation whose value its sender cannot transfer keeps its nonce (regular/skip.go)
  known defects on Allegro:
      avoided: [1] a contract creation whose value its sender cannot transfer keeps its nonce (regular/skip.go)
```

[core/skip.go](core/skip.go) applies the policies; each one lives in the `skip.go` of the domain it
belongs to, next to the note explaining the defect and what to delete once it is fixed:

| | skipped | where |
| --- | --- | --- |
| [1] | a contract creation whose value its sender cannot transfer keeps its nonce | [regular/skip.go](regular/skip.go) |
| [3] | a bundle whose bare root fails keeps what its transaction did | [bundles/skip.go](bundles/skip.go), applied in `Domain.build` |
| [4] | a sponsorship request whose value exceeds 256 bits panics the node | [subsidies/skip.go](subsidies/skip.go), via `unsponsorable` |

Defect **[2]** is the one that cannot be skipped: pre-Allegro, a transaction the state processor cannot
apply keeps the gas it bought although it reaches no block and gets no receipt, because the
snapshot/revert around `ApplyMessage` is gated on Allegro. Skipping it would mean skipping most of what
a pre-Allegro run has to say, so it is tolerated instead — the accounting check accepts that much of a
shortfall, oracle 1 is skipped for a run that hit it, and the run reports what it saw. Allegro fixed it.

The numbering is stable: a defect keeps its number once it is fixed and its case deleted, so an old log
still names the same thing.

Separately, and not a defect of the client: a genesis is written as a single block, and Carmen panics
rather than writing out a node whose hash it has not computed yet, so a genesis carrying more accounts
than the state caches hold used to bring the process down with `unable to store account node with dirty
hash` at around 1536 accounts. `StartIntegrationTestNet` now sizes those caches to the accounts it is
given — the minimum up to about 500, as before, and enough for the trie beyond that — which is what
lets this pool hold 4096. 32768 import in about a second and a half.

## Verifying that the oracles actually bite

A property test that cannot be made to fail is not yet a test. Both of these were confirmed and
reverted:

| Deliberate bug | Caught by | How fast |
| --- | --- | --- |
| `Finalize` keeps skipped transactions in the block | `CheckAbsent` | 4.8 s, all three forks |
| the Allegro blob-hash filter disabled | the model | 8 iterations, and correctly *only* on Allegro and Brio |
| `GetPostTransactions` returns nothing for a fund-backed sponsorship | `CheckPostTransactions` | the first iteration |
| `deductFees` charges one gas too much | `CheckPostTransactions` | the first iteration |

The two sponsorship mutations were applied to `gossip/blockproc/subsidies/subsidies.go` and reverted.
The defects above were not planted: the runs found them, and each cost the model a rule it did not
have — that a carrier is dropped by the scrambler when its sender cannot be recovered, that a bundle
records its plan even when it gives up, that a transaction which merely *reaches* a block is not
enough for the group carrying it.

## Extending it

- **A new field to vary** — add it to the capability that owns it in [core/spec.go](core/spec.go) along with
  what it means, draw it in that capability's `draw` in [core/generators.go](core/generators.go) and [regular/generators.go](regular/generators.go), and price it in
  [core/model.go](core/model.go). A field belonging to only some types wants a capability of its own, embedded by
  those types. The model must be written from the specification, never by calling the validator it is
  checking.
- **A new transaction type** — declare it in `regular` as the capabilities it carries, give it
  `TxType()`, `TxData()` and `Draw()`, and register it in `txTypes`. The compiler then only lets it
  draw and assemble what it actually has.
- **A new family of transaction** — a `core.Domain` of its own, in a package of its own. Wrap another
  domain's generator and rules if the family is that one under different terms, as `subsidies` does,
  or carry a batch of them, as `bundles` does. Nothing needs to change in `core` unless the family
  needs the harness to observe something it cannot see today — which has happened once, for the
  transactions a bundle puts in a block without anybody injecting them (`Extra`).

  Two things the bundles domain learned the hard way, worth knowing before writing the third: the
  model must be told what the *production builder* does to what it is given (it stamps a marker on
  every transaction of a bundle, signs them itself, and promotes a legacy one), and a domain that
  wraps another must correct the *spec* rather than its own prediction when the two disagree — a spec
  that lies about the transaction it became is a model that cannot be trusted anywhere else.
- **A new enum** — add a `//go:generate go tool stringer -type=X -trimprefix=X` directive under its
  doc comment and run `go generate ./tests/transaction_properties/...`. `stringer` is pinned as a
  module tool, so nothing needs installing.
- **A counterexample** — the shrunk batch and the seed that produced it are in the failure message,
  which is the whole of it: `core` turns rapid's fail files off (`-rapid.nofailfile`), because rapid
  otherwise writes each one under `testdata/rapid/` and replays every file it finds there before
  drawing anything new — so yesterday's counterexample, against a harness that has since changed, is
  what the next run spends its first iterations on. Feed the seed back with `-rapid.seed` instead.
